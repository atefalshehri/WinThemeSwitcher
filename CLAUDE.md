# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Windows tray app (Rust) that swaps the full Windows **theme** (wallpaper + colors + light/dark mode) at local sunrise/sunset — macOS's auto-theme behavior, on Win11. Primary apply path is the `IThemeManager2` COM interface (the same one the Settings UWP wraps internally) for atomic, in-process theme apply; a two-tier fallback (legacy `ShellExecute(.theme)` → registry-only DWORD toggle) handles the case where the COM interface errors or its apply doesn't take effect. ~510 KB single-exe (no VC++ redistributable needed — only the OS-provided UCRT), signed Authenticode, no installer.

Roadmap, per-version release plan, and the patch-vs-minor versioning rules live in README.md → Roadmap. v0.5.0 (release pipeline via `scripts\release.ps1`, first non-prerelease release, custom-theme fixes, tray-icon 0.25) shipped 2026-09-28. v0.5.1 (pure bug fixes from an October 2026 review: tier-1 read-back, config-load races, long and respelled `.theme` paths) shipped 2026-10-31 — the first release published with immutable releases already on, so the first real run of `-Publish`'s immutability and attestation checks (all passed). v0.6.0 (the behavior fixes that were under README → Roadmap → Foundation, starting with the `windows-sys` 0.61 update: the coordinate checks and the rounding of Windows Location readings, a Toggle standing a pending retry down (with `settle_tick`), a single-instance lock that can't be opened counting as already running, theme paths on network locations refused, the third-party license notices (`THIRD-PARTY-NOTICES.txt`), the Windows Location lookup held to 15 s on a thread of its own, first-run location dialogs that say what actually happened, the autostart and app-folder fixes — no registration from a temporary folder, a folder where config.json can't be created reported, a Refresh that can't recreate config.json keeping the settings, missing Run and Personalize keys created, Windows' Startup-settings switch logged, an empty config.json repaired with `auto_start` as registered —, and an application manifest and a version resource in the exe (`app.manifest`, embedded by `build.rs`: themed, DPI-aware dialogs; a name and version for Task Manager and Explorer) with the running version logged at start as `app_start version=…`) shipped 2026-11-11; next up is the tier-2 patch (v0.6.1) and then **v0.7.0**'s CA signing with a Certum Open Source certificate. The roadmap was re-evaluated and the CA chosen on 2026-10-31; SignPath Foundation was set aside because its terms require a public track record this project doesn't have yet. ## Source tree vs deployed binary — read first

The source tree (`C:\Users\atef\Documents\Projects\WinThemeSwitcher\`) is kept for future tweaks. **The actually-running binary lives elsewhere** — since 2026-10-31 in the per-user folder README recommends, which `build.ps1` deploys to by default:

```
%LOCALAPPDATA%\Programs\WinThemeSwitcher\
├── win-theme-switcher.exe   ← auto-starts at login
├── config.json              ← coords from Windows Location, auto_start: true
└── events.log               ← diagnostic log (see "Reading events.log")
```

`HKCU\Software\Microsoft\Windows\CurrentVersion\Run\WinThemeSwitcher` points at that exe (with `auto_start` on, the app points the value at its own exe at startup and on Refresh, unless config.json fails to parse or — from v0.6.0 — the exe runs from a temporary folder — §4). The folder inherits its ACL from `%LOCALAPPDATA%\Programs`, whose own ACL (inheritance disabled) lets only this account, SYSTEM and Administrators write it; a folder elsewhere under `%LOCALAPPDATA%`, or a `Programs` folder that `New-Item` creates on a machine that lacks one, can inherit more, so check `Get-Acl` on the deploy folder. Until the 2026-10-23 reinstall the app lived in `C:\Tools\WinThemeSwitcher`, which inherited `Authenticated Users:(M)` from `C:\` (any local account could have swapped the exe that auto-starts at login) — don't recreate it. Redeploy with `scripts\build.ps1` (Build section) — it stops the running app, copies, verifies the copy by hash, and relaunches.

**Never relaunch the tray app with a plain `Start-Process` from an agent shell.** A child process inherits the shell's job object and, if the shell runs inside a packaged app's container, its package identity — and then its HKCU writes (the Run value, the theme registry values) go to a private copy-on-write hive instead of the real registry. The Claude desktop app's container has virtualized `%LOCALAPPDATA%` writes in the past (see "Sign every release build"); on 2026-09-27 and 2026-10-31 the agent shell had no package identity, but don't rely on it. `build.ps1` relaunches via `explorer.exe "<exe>"`, which hands the launch to the user's shell (same context as the logon launch). Do the same for any manual relaunch. A deploy from such a shell can be swallowed too (the folder is under `%LOCALAPPDATA%`): on Windows 10 1903 and later, files and folders a virtualized packaged process creates under AppData can land in the package's private store, visible only inside the container (part of the old pfx backup did), and once a private copy exists, writes go to it. The shell could then hash-match an exe the real folder doesn't have. So `build.ps1` refuses to deploy into AppData unless `GetCurrentPackageFullName` proves the process has no package identity (exit 9); create the deploy folder from a normal shell, too.

(The pre-Cargo Manus prototype exe that used to sit at the repo root has been deleted; `/win-theme-switcher.exe` stays in `.gitignore` so it can't be re-committed.)

## Kaspersky false positive — critical context

**Signed builds run without special handling** (since the v0.3.0 IThemeManager2 + code-signing migration). The signed binary (`CN=WinThemeSwitcher Self-Signed` cert trusted via `Cert:\CurrentUser\Root`) collapses the Authenticode-trust signal, and tier-1 theme apply via `IThemeManager2::SetCurrentTheme` removes the `HWND_BROADCAST WM_SETTINGCHANGE` + direct `WM_THEMECHANGED` signals that previously tripped behavior heuristics. **Sign every release build** — unsigned builds resurrect the issue. The README tells *other* users a Trusted-application rule may still be needed for a self-signed build; on this machine it hasn't been since v0.3.0 (still none for the per-user deploy folder as of 2026-10-31 — a fresh build's first start there took ~8–10 s while it was inspected, so `build.ps1` waits up to 20 s for the relaunch). Everything under "Historical" below is context for unsigned-build scenarios.

**Smart App Control is a separate gate.** With it On, Windows blocks the self-signed app and test binaries and cargo's freshly built build scripts, whatever Kaspersky allows — a root you added yourself doesn't count for it. `test.ps1` then fails with "An Application Control policy has blocked this file". Development here needs it Off; see Setting up a dev machine, step 1.

**Dev/test builds (2026-08-03):** KSN flagged fresh unsigned *test* binaries in `target\debug\deps\` (`VHO:Trojan.Win32.Convagent.gen`) — the trust rules are path-based and don't cover them, and KSN's scanner locks each fresh exe faster than a post-build signtool can run. Two-layer fix in place: (1) a Kaspersky **exclusion on the whole `target\` folder**, added by the user (re-create it on a new machine — see Setting up a dev machine); (2) `scripts\test.ps1` builds the test binary, signs it from the cert store, and only then executes it — **run tests via this script, not bare `cargo test`**.

**Web-traffic popups during agent work:** Kaspersky's encrypted-connection scanning can't inspect the Claude app's HTTPS connections and may pop "The website … may not display correctly — Add to exclusions / Disconnect" when an agent fetches documentation. It's harmless; *Disconnect* just costs the agent that page.

### Historical: pre-signing trust setup

The unsigned binary tripped `VHO:Trojan.Win32.Agent.gen` (Rust exe with no Authenticode signature + `HKCU\Run` writes + `HWND_BROADCAST` of `WM_SETTINGCHANGE` + direct `WM_THEMECHANGED` to `Shell_TrayWnd` + WinRT Geolocation = every AV heuristic signal). Plain **path-based exclusions were insufficient** — Kaspersky's Behavior Detection quarantined regardless. The pre-signing workaround was a **Trusted Applications rule** (Kaspersky Settings → Security → Threats and Exclusions → Specify trusted applications) with all checkboxes ticked: Do not scan opened files, Do not monitor application activity, Do not inherit restrictions, Do not monitor child application activity, Allow interaction with Kaspersky interface.

Rules are **path-based**; until the 2026-10-23 reinstall wiped Kaspersky's settings, two existed:
1. `C:\Tools\WinThemeSwitcher\win-theme-switcher.exe` (the old deploy path).
2. `C:\Users\atef\Documents\Projects\WinThemeSwitcher\target\release\win-theme-switcher.exe` (the build output — rewritten by each build).

Signed builds haven't needed them since v0.3.0; after the reinstall only the `target\` exclusion (above) is known to have been re-created.

If a future rebuild gets quarantined anyway (the hash changes and Kaspersky occasionally re-evaluates): drop a 0-byte placeholder at the path first (`Set-Content -Path ... -Value "" -Encoding Byte -Force`), re-add the trust rule while the placeholder exists, then rebuild. Same trick works for new deployment paths.

### When the trust rule is not enough (KSN cloud verdict)

Trusted Applications rules cover File Anti-Virus + Behavior Detection but **not Kaspersky Security Network (KSN) cloud reputation**. KSN can independently flag a fresh hash and pop a hostile two-button modal — *"Disinfect and restart"* / *"Try to disinfect without computer restart"* — with no Skip / Esc / X dismiss option. Both buttons quarantine (choose the no-restart one; the file is a disposable build artifact). Adding a Threats and Exclusions entry mid-modal does **not** clear the in-progress verdict — Kaspersky finishes quarantining anyway, and even subsequent rebuilds can be flagged by `svchost.exe` (the indexer-style scanner running as `NT AUTHORITY\NETWORK SERVICE`) before the popup re-appears.

The reliable workaround for a deploy session is to **right-click the tray K → Pause protection → 15 minutes**, then immediately copy + launch within that window. Once the process is loaded into memory it survives even after protection resumes. `set_auto_start(true)` re-creates the `HKCU\Run` value on each launch/Refresh if it's missing, so a quarantine event that deletes it self-repairs.

## Build

**Always build via `scripts\build.ps1`** — it builds, verifies the linker hardening and the embedded manifest and version resource, Authenticode-signs (with an RFC 3161 DigiCert timestamp), verifies the signature, and deploys in one step. Bare `cargo build --release` produces a fresh-hash unsigned Windows PE; KSN flags first-seen unsigned exes with `VHO:Trojan.Win32.Convagent.gen` on this machine, and the only fix is signing before the binary ever executes. The same caveat applies to `cargo test` — use `scripts\test.ps1`.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "C:\Users\atef\Documents\Projects\WinThemeSwitcher\scripts\build.ps1"            # build + sign + deploy + relaunch
powershell -NoProfile -ExecutionPolicy Bypass -File "C:\Users\atef\Documents\Projects\WinThemeSwitcher\scripts\build.ps1" -SkipCopy   # build + sign only, leave the deployed exe untouched
```

`build.ps1` deploys to `-DeployDir` (default `%LOCALAPPDATA%\Programs\WinThemeSwitcher`; it must exist — create it once, from a normal shell). Deploying to a different folder **moves** the install: every running instance is stopped, and the copy started there (no config.json, so defaults with `auto_start` on) takes over the Run value — copy config.json across, and use `-SkipCopy` to try a build. Exit codes: 0 ok · 1 cargo missing/build failed · 2 exe path not found · 3 no signtool · 4 signing/verification failed · 5 deploy dir missing · 6 copy failed (the stopped instance is relaunched if its exe is still validly signed) · 7 linker hardening missing, or the manifest or version resource missing or wrong (a version that isn't `Cargo.toml`'s included; any failure of `check-hardening.ps1`) · 8 deployed but relaunch not seen within 20 s (Smart App Control On blocks the self-signed exe) · 9 refused to deploy into AppData: the shell has a package identity, or that couldn't be checked. 5 and 9 are checked before building. It builds with `--locked`, which refuses if `Cargo.lock` is out of date with `Cargo.toml` — after a version bump run `scripts\test.ps1` (or `cargo update -w`) first, then commit `Cargo.lock` with the bump. Both scripts `Push-Location` to the repo and restore the caller's location on exit.

**Linker hardening — `.cargo\config.toml`** (v0.4.1): hybrid CRT (`+crt-static` plus `/NODEFAULTLIB:libucrt.lib /DEFAULTLIB:ucrt.lib` — vcruntime linked statically, the OS-provided UCRT dynamically, so no `VCRUNTIME140.dll` dependency for ~21 KB) and `/DEPENDENTLOADFLAG:0x800` (the exe's static DLL imports resolve from System32 only; `main()` additionally calls `SetDefaultDllDirectories(LOAD_LIBRARY_SEARCH_SYSTEM32)` for runtime bare-name `LoadLibrary` calls — together, a DLL planted next to the exe isn't loaded). Two gotchas, both enforced by `build.ps1` (exit 7): cargo finds `.cargo\config.toml` from the **current directory**, not `--manifest-path` (both scripts `Push-Location` to the repo first — `RUSTFLAGS` is refused up front with exit 7, and `check-hardening.ps1`'s PE check, also exit 7, is the backstop for both); and a set `RUSTFLAGS`/`CARGO_ENCODED_RUSTFLAGS` **replaces** the config's rustflags. `scripts\check-hardening.ps1 -Exe <path>` then checks the PE itself — no `VCRUNTIME140` import, and `DependentLoadFlags` (load-config directory, WORD at +0x4E) = 0x800 — called by `build.ps1` and by `ci.yml`, so losing the config can't pass CI. Since v0.6.0 the same script also checks what `build.rs` embeds (next paragraph), still exit 7: the exe must carry an application manifest (`RT_MANIFEST`, id 1, found by walking the PE's resource directory) that has the `asInvoker`, Common-Controls 6.0.0.0 and `PerMonitorV2` statements, the assemblyIdentity version `X.Y.Z.0`, and neither `longPathAware` nor `activeCodePage`; and a version resource (`RT_VERSION`, id 1) whose file and product versions — the strings and the numbers, read with `[Diagnostics.FileVersionInfo]`, the reader Explorer uses — are the `[package]` version of the `Cargo.toml` next to the script's folder (`-CargoToml <file>` names another one), with FileDescription `WinThemeSwitcher`. So an exe with a stale embedded version, or one built without the build script, can't be signed by `build.ps1` or pass CI. Tried 2026-11-11: exit 7 for the HEAD build from before the build script and for a copy of the deployed exe ("has no application manifest"), exit 7 for the new exe against a `Cargo.toml` copy saying 0.6.0 ("says file version '0.5.1' … but Cargo.toml says 0.6.0"), exit 0 for the new release exe and for the test exe. (`$PSScriptRoot` is empty while Windows PowerShell 5.1 binds parameter defaults under `-File`, so the default `Cargo.toml` path is set in the script body.)

**Manifest and version resource — `build.rs` + `app.manifest`** (v0.6.0). `build.rs` has no dependencies and uses neither `rc.exe` nor `mt.exe`: it writes a compiled resource file, `OUT_DIR\resources.res`, by hand — the empty marker entry, then `RT_VERSION` id 1 and `RT_MANIFEST` id 1, both language 0x0409 — and hands it to the linker with `cargo:rustc-link-arg-bins` (link.exe takes a `.res` as an input; `cvtres.exe`, which it uses for that, sits next to it in the MSVC tools). Checked 2026-11-11: the whole file is byte for byte what `rc.exe` 10.0.26100 makes of the equivalent `.rc` (a `VERSIONINFO` block with the same values and `1 24 "<the stripped manifest>"`), so the hand-written `VS_VERSIONINFO` lengths and 32-bit padding are right — repeat that comparison after touching `block`, `version_info` or `res_entry`. `-bins` reaches every build of the bin target, **the unit-test executable included** (seen with `dumpbin` and `check-hardening.ps1` on the test exe: both resources, `DependentLoadFlags` 0x800), so every `test.ps1` run and CI's Test step start an exe with this manifest and these linker flags, and two tests read back what Windows made of the resources (CI and releases → tests). For a target that isn't Windows MSVC the script prints a warning and embeds nothing (GNU ld doesn't take a `.res`); the two tests then print SKIP. The build script's own exe is compiled and run by every cargo command, `check` and `clippy` included, from `target\` like the dependencies' build scripts.
- **`app.manifest`** (repo root; readable, commented) is embedded with its comments and blank lines removed, LF line ends whatever the checkout's, and `{VERSION}` — which must occur exactly once — replaced by `major.minor.patch.0`. It says: assemblyIdentity `WinThemeSwitcher`; `requestedExecutionLevel` `asInvoker`, `uiAccess` false; supportedOS Windows 10/11; `dpiAware` `true/pm` plus `dpiAwareness` `PerMonitorV2` (per-monitor DPI awareness from the first dialog on — before, winit set it when the event loop was built, after the already-running notice and the first-run location boxes); and a dependency on `Microsoft.Windows.Common-Controls` 6.0.0.0 (themed message boxes). **Keep `longPathAware` out** — the app hands long paths to Windows in `\\?\` form itself (§1), and with it `theme_files_on_long_paths_are_read_not_taken_as_keyless` could no longer show the bug it covers — **and `activeCodePage`**, and anything else that changes how Windows APIs behave: `build.rs` fails the build when either word appears outside a comment, and `check-hardening.ps1` refuses such an exe.

The test exe gets the same resource, so its OriginalFilename isn't its own name.

Tried in a scratch crate on 2026-11-11: even without that `Cargo.toml` line, a version bump ran the script again, into a new output folder — the package version is part of the hash in the folder's name. `main.rs`'s `APP_START` takes the same version through `env!("CARGO_PKG_VERSION")`. With the Common-Controls dependency the loader redirects the name to version 6 in Windows' side-by-side store (on this PC `C:\Windows\WinSxS\amd64_microsoft.windows.common-controls_6595b64144ccf1df_6.0.26100.9818_none_…\comctl32.dll`, file version 6.10) — for the static import, although `/DEPENDENTLOADFLAG:0x800` says "System32 only", and for loads by bare name at run time, although `main()` sets `LOAD_LIBRARY_SEARCH_SYSTEM32` as the default. ### Setting up a dev machine

On a new or reinstalled Windows 11 machine, in order:

1. **Smart App Control** — decide first, explicitly. Evaluation blocks nothing *yet*, but it's temporary: Windows ends it on its own and may switch SAC On without asking. With SAC On, Windows blocks the self-signed exe (so the HKCU\Run start at login fails), cargo's freshly built build scripts and proc-macro DLLs, and the test binaries `test.ps1` self-signs; a root you added yourself doesn't count. Developing on the machine therefore needs SAC Off (Windows Security → App & browser control → Smart App Control settings); whether it can be turned back on later depends on the Windows build. A signature from a CA in Microsoft's Trusted Root Program would satisfy SAC for the released exe, but not for cargo's build scripts, which run before anything can sign them.

### Test and lint

**Run the suite via the signing wrapper** (bare `cargo test` produces an unsigned fresh-hash exe that Kaspersky/KSN may lock or quarantine):

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "C:\Users\atef\Documents\Projects\WinThemeSwitcher\scripts\test.ps1"                  # full suite
powershell -NoProfile -ExecutionPolicy Bypass -File "C:\Users\atef\Documents\Projects\WinThemeSwitcher\scripts\test.ps1" riyadh           # name filter
powershell -NoProfile -ExecutionPolicy Bypass -File "C:\Users\atef\Documents\Projects\WinThemeSwitcher\scripts\test.ps1" -Filter "--x"   # pass a harness flag (must use -Filter; PowerShell eats a bare --x)
```

`test.ps1` exits with the harness's code (101 = test failure), 1 on build/launch failure, 3 without signtool, 4 if a test binary isn't validly signed afterwards (checked with `Get-AuthenticodeSignature`, not just signtool's exit code) — it **never runs an unsigned test binary**. Before v0.4.1 it always exited 0: `#![windows_subsystem = "windows"]` makes the *test* binary a GUI-subsystem exe too, and PowerShell doesn't wait for (or record the exit code of) a GUI exe unless its output is piped — the script now pipes through `ForEach-Object`.

Lint — CI runs the same two checks as hard gates (since 2026-10-31):

```powershell
$cargo = "$env:USERPROFILE\.cargo\bin\cargo.exe"
$manifest = "C:\Users\atef\Documents\Projects\WinThemeSwitcher\Cargo.toml"
& $cargo fmt --manifest-path $manifest --check
& $cargo clippy --release --locked --all-targets --manifest-path $manifest -- -D warnings
```

Both are clean at v0.6.0 with clippy 0.1.99 (Rust 1.99), tests included (`--all-targets`); v0.5.1 took clippy's `as_chunks::<2>()` suggestion in `decode_config_text`. CI's toolchain is the floating `stable`, so a new Rust release can add a lint that fails CI with no code change — and a red run also blocks `release.ps1`'s CI gate: fix it (clippy's suggestion usually is the fix) or `#[allow]` it with a reason. Reproduce it with CI's toolchain first: `rustup update stable` (the CI log's rust-toolchain step shows its rustc version), then the two commands above — rustup never updates by itself, and an older local clippy reports clean, rejects an `#[allow]` of a lint it doesn't know (`unknown_lints` is an error under `-D warnings`), and may not compile a suggestion that uses a newly stabilized API (no `rust-version` is set). `-D warnings` goes after `--`, never into `RUSTFLAGS`, which would replace the hardening flags (Build section). Four `#[allow]`s are deliberate: winit's `EventLoop::run` deprecation at its call site (see README → Maintenance notes), `too_many_arguments` on the pure `decide_tick`, and two `permissions_set_readonly_false` in the read-only-target config tests.

## Architecture — `src/main.rs`

Single file, ~10540 lines (~4950 code + ~5590 `mod tests`), event-driven (`build.rs`, ~320 lines, only embeds the manifest and the version resource — Build section). Logs every state transition to `events.log` next to the exe (rotated to `events.log.old` past 256 KB; writes serialized by `LOG_LOCK`, one `write_all` per line).

### 1. Theme apply — three-tier fallback in `apply_theme`

Tiered worst-case-degradation: each tier is more invasive but less reliable than the one above. `apply_theme(&Slot)` walks them top-down, returning a `&'static str` tag for the tier that succeeded (logged in the `applied=` field of the `cause=...` line).

**Slots and modes (v0.5.0).** A *slot* is day (`Theme::Light`) or night (`Theme::Dark`). `resolve_slot(theme, cfg)` resolves it **once per tick or toggle** into a `Slot { theme, file, modes, keyed, rejected }`: `file` is what will actually be applied (after the path policy below and the stock fallback), and `modes` (`Modes { apps_light, system_light }` — the two Personalize DWORDs) are read from **that** file's `[VisualStyles]` `AppMode`/`SystemMode` via the pure `modes_from` (a missing/unknown value takes the slot default and makes `keyed` false — what Windows does with a key-less theme, e.g. high contrast, is undocumented). The caller decides against `slot.modes` and passes the same `Slot` to `apply_theme`, so the target compared and the file applied can never disagree (e.g. a rejected configured file's modes are never used). `sync_decidable(day, night)` = both keyed and their modes differ; when false (same-mode theme pairs, key-less themes) "the screen is in sync" is unobservable — see §2 and §6. The screen is read by `read_modes()` (both DWORDs, REG_DWORD size 4 required, else None + a one-time `modes_read_err` line); registry-only, so the commit_watcher thread may call it.

**Theme path policy (v0.5.0)** — `resolve_theme_file_checked`: a configured `theme_day`/`theme_night` is expanded (`expand_theme_path`: `ExpandEnvironmentStringsW` with the environment the process started with; a relative result joins the **exe's folder**, never the CWD), then `check_theme_path` accepts only an existing file, not on a network location, with a `.theme` extension (ASCII case-insensitive) that isn't the scratch `%LOCALAPPDATA%\Microsoft\Windows\Themes\Custom.theme` (compared canonicalized). **A network location is refused before anything opens the path** (v0.6.0; `on_network`, the first check after `not-absolute`). `on_network` first puts the text in the form Win32 will open — `std::path::absolute`, which is `GetFullPathNameW` (string work, no file system: microseconds for a share on a host that doesn't resolve) and returns a `\\?\` path as given, as Win32 opens that form as written. Win32 resolves `.`/`..`, repeated separators and trailing dots in every other form, and behind `\\.\` a `..` climbs out of the drive letter: `\\.\C:\..\UNC\server\share\…`, `\\.\\UNC\…` and `\\.\UNC.\…` all open the share (each sent a lookup to the server when tried on 2026-11-11). The pure `path_root` then reads that text, `/` counted as `\`: a share (`\\server\share\…`, `\\?\UNC\…`, `\\.\UNC\…` — `\\localhost\…` and `\\wsl.localhost\…` included), a drive letter (`X:\…`, `\\?\X:\…`, `\\.\X:\…`), or neither (a volume GUID, another device name, a path without a drive); behind `\\?\` or `\\.\`, any number of leading `Global\` is skipped first (`\\?\Global\UNC\…` is a share, `\\?\Global\C:\…` is C: — the name leads back to the same device names). A drive letter is a network drive when `GetDriveTypeW("X:\")` returns `DRIVE_REMOTE` (`drive_is_remote`; `check_theme_path_with` takes that question as a parameter for tests). Before, each `is_dir`/`is_file`/`canonicalize` on a theme whose server didn't answer held the event-loop thread for the SMB timeout (21–42 s in the October review) — at startup before the tray exists, on every tick, on Toggle and on Refresh. `GetDriveTypeW` doesn't ask the server; for a drive letter it answers from the process's device map. Measured 2026-11-11 on build 26300: 0.17 µs per call for C:, for a connected mapped drive (whose first real access right afterwards took 0.5 s), and for a drive letter linked the way `net use` links one (`DefineDosDeviceW`, raw `\Device\LanmanRedirector\;X:…` target) to a server name that doesn't resolve; about 1 µs for a letter that isn't a drive (not remote). A relative path is joined to the exe's folder first, so an exe run from a share has its relative theme paths refused too. **Not detected**: a local path that reaches a share through a junction or a symlink; through a `subst` drive that `GetDriveTypeW` doesn't call remote (two links made with `DefineDosDeviceW` in the same test: one straight onto a `\\server\share` path was reported remote; one onto a mapped drive's root returned type 1, "not a drive", so it may not have been a working drive at all — real `subst` drives weren't tried); or through a device name other than a drive letter, which the text can't follow — `\\?\GLOBALROOT\Device\Mup\server\share\…` is the redirector (a lookup of an unresolvable host through it waited like a plain share), and so is any name someone defined to point at one. `path_root` calls these "neither", and `path_root_table` pins the GLOBALROOT row as a known gap. Such a theme is used, and the tray freezes as before while its server is down (README → Known limitations). A drive letter Windows doesn't list at that moment isn't a network drive to the check either: its path is looked at like any local one and comes out `missing`, without a wait (an absent letter fails at once). Whether a remembered mapping that hasn't reconnected reads that way was not tested. It returns the path to use, with the file name as stored on disk (`with_stored_name`, v0.5.1): an 8.3, trailing-dot or differently cased spelling opens the same file, but its stem would become the name tier 1 looks for; the typed spelling stays when the stored name in the typed folder isn't the same file (a symlink to a differently named file). Rejections (`ThemePathIssue`: `missing`, `directory`, `theme-pack`, `not-a-theme`, `scratch-file`, `unexpanded-var` — a `%NAME%` survived, `not-absolute` — drive-relative `C:x.theme`, `network-path` — a share or a network drive, said without looking at what is or isn't there) fall back to the stock theme; `apply_theme` logs `theme_path_rejected slot=… reason=… path="…" expanded="…" using="…"` per apply, and `report_theme_path_problems` shows one non-blocking warning box per config load (startup, Refresh). Empty/whitespace strings count as unset (no log). Stock: `%SystemRoot%\Resources\Themes\aero.theme` / `dark.theme`.

#### Tier 1: `IThemeManager2` (preferred — `applied=theme-manager2`)

Undocumented-but-stable COM interface in `themeui.dll` that the Settings UWP itself wraps. CLSID `{9324da94-50ec-4a14-a770-e90ca03e7c8f}`, IID `{c1e8c83e-845d-4d95-81db-e283fdffc000}`. Vtable layout in the `IThemeManager2Vtbl` struct at the top of `main.rs`.

Flow (`apply_via_theme_manager2`):
1. Resolve the target `.theme` file's `[Theme]` → `DisplayName`. `resolve_theme_display_name` reads it with **`GetPrivateProfileStringW`** (v0.4.1 — Windows' own INI parser, so key/section case, whitespace, quotes, and ANSI-vs-UTF-16 decoding match what Windows itself reads; a hand parser mis-decoded non-English names) via `read_theme_ini`, which uses a sentinel default to tell "absent" from "empty" and first proves the file opens (the API also returns the default when it can't open the file). Paths of 248+ UTF-16 units go to the API in `\\?\` form (`win32_path_arg`, v0.5.1): the exe has no longPathAware manifest, so a plain long path failed to open and every key read as absent. System themes use SHLoadIndirectString-style refs (`@%SystemRoot%\System32\themeui.dll,-2060`), resolved by `resolve_indirect_string`. For `dark.theme` → `"Windows (dark)"`; for `aero.theme` → `"Windows (light)"`. **No `DisplayName` key → the file stem** (v0.5.0; what Windows lists — verified 2026-09-28 by enumerating IThemeManager2 with such a file installed); an empty value → None.
2. `CoCreateInstance(CLSID_THEME_MANAGER2)` + `Init(0)`.
3. Enumerate via `GetThemeCount` + `GetTheme(i)` + `ITheme::GetDisplayName(&BSTR)`, collecting **every** matching index. Free each BSTR with `SysFreeString`. **Don't cache the index across launches** — enumeration order is not stable.
4. `pick_theme_index` (pure, v0.5.0) — ITheme exposes no file path, so a shared name is a hazard. For one of Windows' own themes (`is_windows_theme`: the file sits directly in a folder of `%SystemRoot%\Resources`) the first match wins (`theme_manager2_ambiguous` logged when >1). For any other file: if `name_taken_elsewhere` finds another `.theme` with the same name in the folders Windows lists (`theme_search_dirs`: each `%SystemRoot%\Resources\*` folder, plus the `%LOCALAPPDATA%\Microsoft\Windows\Themes` tree; the configured file itself excluded by canonical path), or there are 0 or ≥2 matches → Err, and tier 2 applies the configured file by exact path.
5. `SetCurrentTheme(NULL, idx, apply_now=1, apply_flags=NO_HOURGLASS, pack_flags=0)`. This is the only tier-1 call that applies; it does the WM_THEMECHANGED + WM_SETTINGCHANGE broadcasts internally.
6. **Read-back** (v0.5.1): `pre = read_modes()` is taken right before SetCurrentTheme; once it returns success (and `mgr` is released), `tier1_readback` reads the modes every 100 ms for up to 2 s (`READBACK_WINDOW`) until they equal `slot.modes`. The pure `readback_verdict` gives `Reached`; `Unverifiable(reason)` — from `unverifiable_reason` (slot not keyed, or `pre` already the target: the same predicate as commit_watcher's skip), or `unreadable` when no reading succeeded; or `NoOp(last reading)`. `NoOp` logs `theme_manager2_noop` and `apply_theme` falls through to tier 2 exactly as on an Err; the others log `theme_manager2_apply … readback=… readback_ms=…` and return `applied=theme-manager2`. Main thread, registry reads only; a NoOp blocks the event loop for the 2 s. Whether Windows writes the modes before SetCurrentTheme returns is undocumented — `readback_ms=0` on a `readback=reached` line means it does. On this machine (Windows 11 build 26300) it does: on 2026-10-31 Toggle Theme in both directions logged `readback=reached readback_ms=0` (SetCurrentTheme `after_ms` 149–198).

Why this is the primary path: ShellExecuteW(`.theme`) silently fails when the user isn't actively interactive (post-WTS_SESSION_UNLOCK, scheduled while away, no foreground UI). The UWP activation pipeline swallows the apply request — Settings flashes briefly but never commits. `IThemeManager2` is in-process, has no UI dependency, and is what every serious tool uses (AutoDarkMode, wtheme, etc.). Apply latency is ~200 ms vs. the ~5 s poll-then-fail of the legacy path.

**STA threading is mandatory** for this interface ("Shell crap is always STA" per AutoDarkMode source). The main thread already calls `CoInitializeEx(None, COINIT_APARTMENTTHREADED)` at startup; tier-1 apply runs from winit event handlers on that same thread, which is correct. **Never call from a worker thread** without CoInitializeEx(STA) on it first — you'll get RPC_E_WRONG_THREAD or silent corruption.

#### Tier 2: `ShellExecuteW(.theme)` + `commit_watcher` (legacy — `applied=theme-file`)

Fires only if tier 1 errors out (logged as `theme_manager2_err target=… slot=… msg="…"`) or its read-back finds no effect (`theme_manager2_noop`). `ShellExecuteW("open", <.theme path>, ..., SW_HIDE)` launches the Themes UWP, plus a `start_settings_closer` thread to `PostMessage(WM_CLOSE)` the Settings window once it appears, plus a 300 ms sleep + `poke_shell` (taskbar repaint). (Known issues, planned for the tier-2 patch after v0.6.0: the closer matches English titles only, can close a Settings window the user had open, and posts WM_CLOSE before the theme commits; the 300 ms sleep, `poke_shell` and tier 3's broadcast run on the event-loop thread; and `poke_shell` finds only one `Shell_SecondaryTrayWnd`, so a third monitor's taskbar isn't poked — whether the system-wide broadcasts alone repaint it is untested.)

**`commit_watcher` is the safety net for tier 2's silent-fail mode** — `start_commit_watcher(slot, pre)`, `pre` = `read_modes()` taken just before the ShellExecute: spawns a thread that polls `read_modes()` every 200 ms for 5 s against `slot.modes`. If it never matches → logs `commit_timeout target=… actual=…` and **falls through to tier 3 from inside the watcher thread** — writes the registry directly, broadcasts, pokes shell, polls again to confirm, logs `fallback_registry target=… confirmed=true after_ms=…`. When the modes can't show whether the apply committed (`unverifiable_reason`, shared with tier 1's read-back) — the slot isn't `keyed` (forcing guessed modes over the theme would be wrong) or `pre` already equals the target — it logs `commit_unverifiable target=… slot=… reason=modes-not-in-theme-file|already-matching` and starts no thread.

With stock themes, or custom themes Windows lists under a unique name, a healthy tier 1 means this path is rarely entered — it's the backup in case a future Windows build breaks the COM interface. A theme tier 1 refuses by design (tier 1, step 4: not listed by Windows, or its name taken by another `.theme` file) takes this path at every switch.

#### Tier 3: registry-only (last resort — `applied=registry`)

`write_theme_registry(slot.modes)` writes `AppsUseLightTheme` then `SystemUsesLightTheme` to the slot's modes, then the caller broadcasts `WM_SETTINGCHANGE("ImmersiveColorSet")` to `HWND_BROADCAST` and calls `poke_shell`. **Sets the theme's light/dark modes but not its wallpaper.** Both `RegSetValueExW` results are checked (v0.4.1), stopping at the first failure; any failure returns `Err` (so tick's bounded retry runs), and a half-written pair still broadcasts before returning. Since v0.6.0 the registry work is `write_modes_at(key, modes)` (the key a parameter, so tests use a throwaway one; `write_theme_registry` passes `THEME_KEY` and does the half-write broadcast), a missing Personalize key is created (`open_hkcu_key(.., create_missing = true)`: `RegOpenKeyExW` first, `RegCreateKeyExW` only on `ERROR_FILE_NOT_FOUND` — every profile has the key, so this only matters after a deliberate deletion), and the open error carries the API and its code (`RegOpenKeyExW Personalize rc=5`; it used to be a bare "RegOpenKeyExW failed for Personalize"). `read_modes` never creates the key. Write order no longer protects the retry gate (with two values compared, any half state is visible): what protects it is that `tick` takes the failure baseline from a `read_modes()` made **after** the failed apply (§2).

**`poke_shell`** sends `WM_THEMECHANGED` + targeted `WM_SETTINGCHANGE("ImmersiveColorSet")` to `Shell_TrayWnd` and `Shell_SecondaryTrayWnd`, then `DwmFlush()`. Required for tiers 2 and 3 — tier 1 broadcasts internally. If future Win versions add new taskbar window classes, extend the list.

Custom user themes work with tier 1 only if they're registered with Windows (installed via Settings → Themes) under a unique name; otherwise tier 1 errors (`no installed theme matches DisplayName "…"`, or the shared-name refusal) and tier 2 takes over.

### 2. Event loop — only tick on specific events

The run closure must **not** call `tick()` on arbitrary events: a theme change in Settings broadcasts `WM_SETTINGCHANGE`, and a tick on it would see `current != target` and revert the user's choice. `tick()` runs only on:

- `Event::NewEvents(StartCause::Init)` — first event after launch.
- `Event::NewEvents(StartCause::ResumeTimeReached { .. })` — **only when `plan_wake` says so**: the armed deadline is due, or a clock step was detected (below). A heartbeat wake that is neither just re-arms.
- `Event::UserEvent(AppEvent::Menu(refresh_id))` — user clicked Refresh.
- `Event::UserEvent(AppEvent::Wake(_))` — session unlock / power resume (§5; safe because these never fire on a Settings theme change).

`Event::NewEvents(StartCause::WaitCancelled { .. })` (any other wake: tray/menu input, broadcasts) never ticks; it re-runs `plan_wake` and either re-arms or, if the plan is Tick (a clock step, or the wall-clock deadline already due), arms `Instant::now()` so the next ResumeTimeReached ticks. `AppEvent::TrayProbe` (§6) never ticks. Everything else is `_ => {}` (the Menu arm also handles Toggle Theme, Open Config and Quit, which don't tick).

**Wall clock vs. monotonic clock (v0.4.1).** The schedule is wall-clock, winit's `WaitUntil` is a monotonic `Instant`, and the mapping breaks when the system clock is *stepped* — on this machine every boot after an Ubuntu session (Ubuntu keeps the RTC in UTC, so Windows starts 3 h behind until w32time steps it forward; Kernel-General event 1 shows the +3 h jump). Before v0.4.1 the Init tick decided from the wrong time and the deadline fired up to 3 h late. Now `tick()` records `TickState.armed` (wall deadline, via `arm()`) and `TickState.mark` — the (wall, mono) readings the tick *decided* from, so a step during a slow apply is still detected; `plan_wake(armed, mark, now_wall, now_mono)` — pure, unit-tested — returns `Tick{step_ms}` when `|wall advance − mono advance| > 60 s` (`CLOCK_STEP_MS`) or the deadline is due, else `Arm(min(deadline, now + HEARTBEAT))`. `HEARTBEAT` is 10 min, so a step is caught even if the `WM_TIMECHANGE` broadcast (which reaches winit's hidden top-level window and wakes the loop immediately) never arrives. The tick that consumes a step — the `cause=clock-jump` tick, or a wake/Refresh that got there first — logs `clock_jump step_s=±N consumed_by=<cause>` (pure helper: `detected_clock_step`). A suspend shouldn't register as a step: on Windows `Instant` is QPC-based, and QPC keeps counting during sleep (a `clock_jump` line right after a resume would mean otherwise; the tick it causes is harmless). Accepted (README → Known limitations): only `tick()` renews the mark — heartbeat and `WaitCancelled` wakes never re-mark — so at polar latitudes, with the next transition weeks away and no lock, sleep, Refresh or restart in between, ordinary drift between the wall clock (which w32time corrects) and the monotonic clock can add up past `CLOCK_STEP_MS`. That costs one `cause=clock-jump` tick, normally `applied=skip` or `skip-override` after a misleading `clock_jump` line; the tick re-marks, so it recurs only after another such stretch.

**State-aware apply**: `tick` resolves both slots (§1), picks the scheduled one, and decides via the pure `decide_tick(kind, current: Option<Modes>, target: Modes, now, next, clock_stepped_back, sync_decidable, &TickState)` → `Apply` / `SkipInSync` / `SkipOverride` / `CancelRetry`, called with the **pre-tick** state; the outcome is recorded once the apply result is known, by the pure `settle_tick(state, kind, outcome, now, next) -> Settled { deadline, retry }` (v0.6.0 — everything a tick records about its outcome goes through it, and `tick` then arms the returned deadline together with the clock mark, so the step from outcome to saved state and next deadline is unit-tested; a tick without location returns before it and records nothing). `TickOutcome::Reconciled` (a successful apply — `tick` also calls `note_applied_slot` — or any skip) → `note_reconciled`, deadline = the next transition; `TickOutcome::ApplyFailed { after }` — `after` is `read_modes()` taken AFTER the failure — → `note_apply_failed`, deadline = the retry's, or the next transition once the budget is spent; `now` is read after the apply, so a retry is timed from the failure. `sync_decidable = false` only disables the `SkipInSync` branch (equal modes prove nothing): Init re-applies every launch, a wake inside the window reads as `skip-override`, and override preservation and the retry stand-down still use the real readings. **Refresh always applies** (config edits take effect immediately), and a Refresh whose apply fails starts a fresh retry budget (`settle_tick` clears the episode before counting the failure). **Bounded apply retry (v0.4.0)**: a failed apply reschedules to `min(next_transition, now + 60 s)` for up to 3 consecutive attempts (log field ` retry=N`, then ` retry=exhausted`; budget resets per episode, and exhaustion clears `reconciled_next` so later wakes still retry instead of "preserving" the failure). The retry arrives as a normal Scheduled tick; `retry_baseline` (the modes read right **after** the failure — so a partial effect of our own apply, like a tier-3 write that flipped one value, is part of the baseline and never mistaken for a move; this was the v0.5.0 design review's blocker) gates it — if the screen moved off the baseline (either value) within the episode's window (`now < episode_next`), the user intervened and the retry stands down (`applied=skip-user-intervened`); an unreadable reading on either side never counts as a move. **A Toggle stands it down too** (v0.6.0): the Toggle handler calls the pure `note_toggle(state, applied)`, which sets `TickState.retry_toggled` when the Toggle's `apply_theme` returned Ok and a retry is pending (and does nothing otherwise), and the gate treats that flag like an observed move, inside the same window. The modes alone showed only an odd number of Toggles — a second one lands back on the baseline, and through v0.5.1 the retry then reverted it — and none at all with two same-mode themes or an unreadable registry. Every new failure clears `retry_toggled` (the baseline is new), and so does whatever ends the episode (a reconciled tick, exhaustion, a failed Refresh's fresh start). A Toggle whose apply failed isn't recorded: in the ordinary case (the screen still on the other slot's theme) it was aiming at the scheduled theme, which the retry then delivers; one that failed after changing one of the two values does read as a move, as before. Accepted: "returned Ok" is not "committed" — a tier-2 Ok means ShellExecute launched, and tier 1 returns Ok when its read-back can't tell — so a Toggle that silently did nothing also stands the retry down (a tick's own apply is recorded as reconciled on the same basis); and the flag exists only while a retry is pending, so once the budget is exhausted a Toggle is applied over by the next wake unless it lands on the scheduled theme (wakes are free retries then; README → Known limitations). The retry only covers *total* apply failure (all three tiers, realistically a failed registry write); a tier-2 ShellExecute silent-fail recovers via commit_watcher's registry fallback instead.

Scheduling math: `schedule(now_utc) -> (Theme, next_utc)` is the single source of truth (unit-tested). It collects sunrise/sunset instants for the **UTC** dates D−1..D+1 via the `sun-times` crate, sorts them as instants, and picks state-after-last-event ≤ now / first-event > now. **Never pass a local date to `sun_times`** — it takes a UTC date and keys events to the solar day; passing a local date made UTC+13/+14 permanently dark and skipped post-midnight sunsets (fixed v0.3.2). **Polar latitudes (v0.4.1):** at `|lat| >= POLAR_MODEL_LAT` (65.5° — whole days without sunrise/sunset start at ~65.73°) the schedule uses **only** the solar-altitude model: current from `altitude_theme` (`solar_altitude_deg` — local implementation, the crate's `altitude` has math bugs — vs. the −0.833° civil threshold), next from `next_altitude_flip` (`next_altitude_crossing` in 48 h chunks up to 200 days; probes at least 15 s apart — so whether a short polar "day" is found doesn't depend on the start time — and further apart when the sun is far from the threshold, since the altitude changes ≤ 15.04°/h × |cos lat|; bisected to 1 ms and returned on the far side of the crossing). Mixing `sun_times` in at polar latitudes is what broke before: after the last sunset before the midnight sun it reports no following sunrise (~68 days of Dark in Tromsø), and a design that switched between the two models per UTC date made them disagree at midnights — phantom transitions that reverted overrides, and minute-long flickers (both caught in the v0.4.1 reviews). One model per location makes the **contract** hold by construction: the theme stays `current` for every instant in [now, next), and `next` is a real flip — unit-tested by `schedule_contract_holds_around_polar_edges` (Tromsø, Pevek, McMurdo). Below 65.5° (Reykjavik included) `sun_times` alone decides, unchanged. Everything is pure math on UTC instants; `tick` converts to `Local` only for logging.

### 3. Location (WinRT Geolocation)

`try_get_windows_location() -> Result<(f64, f64), LocationFailure>` is one lookup, held to `LOCATION_LOOKUP_CAP` (15 s; v0.6.0 — the cap, the lookup thread and the reasons are the next two paragraphs). `lookup_windows_location(cap)` runs `query_windows_location()` — the `windows` crate's `Geolocator::RequestAccessAsync().get()` → `GetGeopositionAsync().get()` — on a thread of its own through `run_with_timeout`, and the pure `settle_location` turns what came back into the result: a reading goes through the pure `usable_location` (v0.6.0), on the caller's thread, which returns the reading to keep or the reason it can't be used; a rejected reading is logged as `location_rejected reason=…`, without the values, and counts as no location (`LocationFailure::Rejected`, which at first run gets a dialog of its own, below). `out-of-range`: not a place on Earth (`valid_coordinates`: latitude within ±90, longitude within ±180, so NaN and the infinities fail), checked before rounding so a reading just past a limit isn't rounded into range. `zero`: exactly 0/0, which a `Config` can't tell from "no location yet" (v0.5.1 kept it, saved it, and then silently never switched). Any other reading is rounded by `round_coordinates` to 2 decimals, 3 when the reading's latitude is 60° or more (`FINE_COORDINATES_LAT`), with a rounded `-0.0` turned into `0.0`, and left unrounded if rounding would give 0/0. All three callers (first run's `acquire_location`, the broken-config startup, Refresh) get the rounded pair, so the session's schedule and the saved file agree. **Only readings are rounded**: coordinates already in config.json — hand-typed, or saved at full sensor precision by v0.5.1 and earlier — are never rewritten. With Location on, this PC's lookups took 0.5–1.4 s for a process's first one and 32 ms for the next (2026-11-11). The caller still waits for it: at startup it is called **before** `event_loop.run`, so the tray icon doesn't appear until the lookup has ended or the cap has passed, and at a Refresh it holds the event-loop thread for the same time; v0.8.0 moves the lookup off the startup path.

**The cap and the lookup thread (v0.6.0).** Through v0.5.1 both `.get()` calls ran on the main thread and held it for as long as Windows took: a position gives up after 60 s by itself (7 s in Connected Standby, per the `GetGeopositionAsync` reference), and `RequestAccessAsync` has no limit at all. `run_with_timeout(thread_name, limit, work) -> Result<T, NoAnswer>` (generic, unit-tested with fast, blocked and panicking work) spawns a named thread and waits on a one-slot channel with `recv_timeout`: the value, `NoAnswer::TimedOut`, or `NoAnswer::WorkerLost` (the thread couldn't be started, or ended without a value — a panic in a build that unwinds; the release build aborts). **On a timeout the caller goes on and the worker is abandoned**: it finishes or hangs by itself, and its late value goes into a channel whose receiver is gone and is dropped there, in the worker. So the work must own everything it touches. `query_windows_location` uses only its own WinRT objects and returns the raw reading or a `LocationFailure`; it never touches the config, the registry, the log or the UI, and a lookup's coordinates exist outside it only as `settle_location`'s return value. A Refresh while an abandoned lookup still waits starts another thread next to it; each ends when Windows answers (one that never gets an answer stays until the app exits — a thread blocked on an event). The overload `GetGeopositionAsync(maximumAge, timeout)` was not used to end the worker sooner: its `maximumAge` changes which cached position is accepted, and the plain call's own 60 s is short enough for a thread nobody waits for.

*Apartment.* The lookup thread never calls `CoInitializeEx`. `keep_mta_alive()` calls `CoIncrementMTAUsage` once per process and never gives the cookie back: per its reference it "creates the MTA, if the MTA does not already exist" and "puts the current thread into the MTA, if the current thread is not already in an apartment" — the case it names is an implementation that needs COM initialized without caring which apartment — and a later lookup thread, which doesn't call it again, is in that apartment implicitly. A per-thread `CoInitializeEx(COINIT_MULTITHREADED)` would have to be balanced by a `CoUninitialize` that an abandoned thread never reaches, and the last balanced one would tear the apartment down under the activation factories windows-core caches. windows-core 0.59 does the same by itself when `RoGetActivationFactory` returns `CO_E_NOTINITIALIZED` (`imp/factory_cache.rs`: `CoIncrementMTAUsage`, cookie dropped, retry); the app's own call only makes that independent of the crate version (`windows` 0.62 is planned for v0.8.0). Blocking in `.get()` is ordinary on an MTA thread — the crate's `get` waits on an event, and its completion handler is agile, which is also why the same call never deadlocked on the main STA — and `Geolocator` is `MarshalingBehavior(Agile)`, `Threading(Both)` in its reference. The main thread stays the STA `ensure_com_initialized` makes, and nothing about theme apply moved.

*`RequestAccessAsync` off the UI thread.* Its reference says "You must call this method on the UI thread, otherwise an exception will occur", with the app in the foreground. That is written for packaged apps, whose consent prompt belongs to their window; no Microsoft page found says what holds for an unpackaged desktop app, which has no UI thread in that sense — through v0.5.1 the app called it on the main thread before any window existed. The `GeolocationAccessStatus` reference names the answer such a request may get instead of an exception: `Unspecified` — "Permission request failed due to an error condition. This may occur if the request wasn't made from the UI thread or if the app wasn't in the foreground" (`Denied` is "The user has denied location access or location is disabled by system policy"; read 2026-11-11). So `Unspecified` is an outcome to expect, not a curiosity, and it keeps wording of its own that names no cause. Whether the move to the lookup thread changes what Windows answers is unknown: v0.5.1's call, from a main thread without a window in a process that wasn't in the foreground, arguably met the same condition, and neither version was run with Location off. So this rests on a test, not on documentation: on this PC (build 26300, Location on and allowed for desktop apps, 2026-11-11) `the_real_windows_location_lookup_ends_within_the_cap_whatever_windows_says` got "allowed" and a position from the lookup thread, both for the thread that created the MTA and for a second one — and with the caller set up as in the app: the test thread makes itself a single-threaded apartment first (`ensure_com_initialized`; the process's first, so COM's "main" STA, printed as `caller=main-sta`) and then waits in `recv_timeout` without pumping messages, so a lookup that needed that apartment would have shown up as a timeout. **Not checked**: Location off, a denial, an error, Windows' own prompt, and the app itself (it isn't started from an agent session, and the installed copy has coordinates, so it never looks up). Worth one manual first run, by the maintainer from a normal shell: Location services off on a 24H2+ PC, a `-SkipCopy` build copied to a scratch folder without config.json (quit the installed copy first — single instance — and start it again afterwards, so the Run value points back at it), noting whether Windows' prompt appears, whether `RequestAccessAsync` waits for the answer past 15 s, and which `reason=` the log has. "Changes to API behavior for Wi-Fi access and location" (Win32 docs) says that from Windows 11 24H2 an app without location consent gets a one-time system prompt at its first `RequestAccessAsync`; whether the call waits for the answer isn't documented and wasn't observed here (it would take turning Location off on this PC). If it does wait, the cap changes that first run: through v0.5.1 the app waited for the answer and then had its location; now an answer that takes longer than 15 s comes after `reason=timeout`, whose box says to answer Windows' question first and then choose Refresh.

**Why there's no location** — `LocationFailure`; `try_get_windows_location` logs one `location_lookup_failed reason=… after_ms=…` line per failed lookup (`location_failure_line`, pure), never a coordinate:

- `Denied` (`reason=access-denied`): `RequestAccessAsync` answered Denied — Location is off, or not allowed for apps. `Unspecified` (`access-unspecified`): it answered Unspecified, or a value the app doesn't know (`access_answer`, pure — an unknown value is neither "allowed" nor a denial).
- `TimedOut` (`timeout`): no answer within the cap; `after_ms` is the cap.
- `Failed { stage, hresult }` (`error`, with ` stage=… hresult=0x…` appended): the call that failed — `apartment` (`CoIncrementMTAUsage`), `request-access`, `geolocator` (`Geolocator::new`), `position` (`GetGeopositionAsync`, which per its reference also fails when the app has no permission or its own 60 s pass), `reading` (the coordinate out of the position) — and its HRESULT; `stage=worker hresult=0x00000000` is `NoAnswer::WorkerLost`. An access-denied HRESULT at `stage=position` stays an `error`: only `RequestAccessAsync`'s own answer counts as a denial. A deliberate choice, kept after review: "allowed" followed by a refused position hasn't been observed, the "not allowed" wording must not rest on an error code, and the error box still names Privacy & security > Location — what that case loses against v0.5.1 is the offer to open Settings for the user.
- `Rejected(reason)` (`reading-rejected`, with ` reading=zero|out-of-range`): `usable_location` refused the reading; the `location_rejected` line comes first, unchanged.

The three callers differ only in what they do with the result. First run (`acquire_location`) persists a location, and otherwise explains (next paragraph). The broken-config startup uses a location in memory only and shows nothing about a failed lookup (the config error is what the user has to deal with). Refresh persists a location; a failure is only logged, and the tick that follows logs `skipped=no-location` (a dialog for a Refresh that fails is v0.8.0's).

**First-run dialogs (v0.6.0; REVIEW finding 12)** — `explain_missing_location(failure, tray_exists, config_on_disk)`, called from `acquire_location` only. They come up before the event loop and the tray icon exist, so each box blocks startup until it's closed. The texts are built by pure functions from what happened — the failure, whether Settings could be opened, whether the tray icon exists yet (`acquire_location` passes `false`, the only value today; the `true` wording is there for v0.8.0, when the lookup moves behind the tray), and whether there is a config.json to type into (`Loaded::from_file`, false in a session whose config.json couldn't be created, §4) — and the tests check each sentence against the situation it is shown in. Through v0.5.1 one box said "off or not allowed" for every failure, the next spoke of "the Settings window that just opened" without checking that it had, and both sent the user to a tray icon that didn't exist yet.

- `location_prompt(failure, tray_exists, config_on_disk)` picks the first box. `LocationPrompt::OfferSettings(text)`, a Yes/No box, for `Denied` — "Windows Location is turned off, or apps are not allowed to use it", the only text that says so as a fact — and for `Unspecified` ("did not say why… may be turned off, or blocked for apps"). `LocationPrompt::Inform(text)`, one OK box, for a timeout ("did not answer within 15 seconds" — the number is the cap's — and "If Windows is showing a question about location access, answer it, then close this message and choose Refresh (step 1 below)": the answer that comes after the cap is dropped, so answering Windows isn't enough), an error ("the lookup failed") and a rejected reading ("a location for this PC that WinThemeSwitcher cannot use"), each with the two next steps: Refresh later, or Open Config in the same menu to type the coordinates "in decimal degrees (south and west are negative)" — said here too because this path never shows the manual-setup box, and a west or south value typed without its minus is a valid place that no check catches. Step 1 ends with `REFRESH_IS_SILENT` — "Refresh does not say whether it found the location: if the theme still does not change at the next sunrise or sunset, it most likely did not" — because a Refresh shows nothing about its lookup either way, and the box would otherwise ask the user to judge something they can't see. **No offer to open Settings there, and config.json isn't opened unasked**: nothing says Location is off, so the box only adds "If this keeps happening, check that location is turned on" under Privacy & security > Location — and not even that for a rejected reading, which no switch changes. With `config_on_disk` false no text sends the user to a file that isn't there: the Yes/No box's second line is "No: go on without a location for now", and step 2 says the coordinates can't be typed in yet, because config.json could not be created, and to move the app to a folder that can be written first (`NO_CONFIG_FILE`).
- Yes → `open_location_settings()`: `ShellExecuteW("ms-settings:privacy-location")`, returning whether the result was > 32 (`launch_accepted`, pure, which `open_config_in_editor` uses too; a refusal logs `open_settings_err code=N`) → `location_settings_followup(opened, tray_exists)`, which also ends with `REFRESH_IS_SILENT`: "Windows Settings should now be open on its Location page. If it is not, open Settings yourself and go to Privacy & security > Location", or "Windows Settings could not be opened from here. Open Settings yourself (Start > Settings) and go to…". "> 32" means the launch was accepted, not that the page is on screen — hence "should", and the way there by hand in both. It then says what must be on rather than which switch to flip — "turn location on and let apps use it, desktop apps included" — with the names as a guide ("Location services", "Let apps access your location", "Let desktop apps access your location", "or something close to that, and a PC may not show all of them"), and that location turned off for the whole PC takes an administrator. Where the names come from: Microsoft's support page "Windows location service and privacy" gives the path Start > Settings > Privacy & security > Location, "Location services" (a setting for administrators) and "Let apps access your location" (per user); Microsoft's Edge article "Resolve Edge Location service problems on Windows" (dated 2026-04-01) lists all three toggles for Settings > Privacy & security > Location, in the order the box names them, with "Let desktop apps access your location" further down the page. The support page's Windows 11 section names no switch for desktop apps (its Windows 10 section has "Allow desktop apps to access your location"), so that name rests on the one article; none of the three was read off this PC's Settings page. The wording is meant to hold if one is missing or renamed.
- No → `manual_setup_text(tray_exists)`, then `open_config_in_editor()` — now returning whether anything was launched — and, only when nothing was, `config_not_opened_text(path)` with the file's path, in a non-blocking box (`show_warning_async`), so the icon the previous box announced does appear. The manual box says what happens when it's closed: config.json opens "in the program set up for .json files, or else in Notepad", and "If neither can be started, another message says where the file is". When there is no config.json (`config_on_disk` false), No shows `no_config_file_text()` instead and opens nothing. Otherwise the manual box would promise a file to save, and `open_config_in_editor` would start Notepad on a path that doesn't exist: `ShellExecuteW`'s result says only that Notepad was started, so the function returns true and no path box follows (read from the code; not run). The tray's Open Config in such a session still does exactly that (unchanged, outside this work).
- Every box that sends the user to Refresh first says where the icon is (`tray_icon_sentence`): before the tray exists, "After you close this message, the WinThemeSwitcher icon appears in the notification area at the end of the taskbar (it may be behind the ^ arrow)". The first box of the Yes/No path doesn't mention the icon; the box after it does. Plain words only: no API names, codes or stage names on screen (they're in the log).
- Unchanged: the order of the boxes and how they stack with the window they follow (the follow-up is an unowned box created right after Settings is launched, as in v0.5.1; Settings may come up over it, and startup and the tray icon wait until it's closed. A review proposed `MB_TOPMOST` for it; not adopted without a look at the screen, since a topmost box can sit over the very switches it describes — to be decided with the manual first run above). **None of the boxes was looked at on screen** — the app isn't started from an agent session — so line breaks and length are as written, not as seen.

`open_config_in_editor` opens `config.json` with the `.json` "open" handler if one exists (`AssocQueryStringW(ASSOCF_INIT_IGNOREUNKNOWN, ASSOCSTR_FRIENDLYAPPNAME)` — the flag makes a missing association fail instead of resolving to the "How do you want to open this file?" picker, which is what happens on this machine; FRIENDLYAPPNAME also covers Store-app handlers), else `System32\notepad.exe` by full path (`GetSystemDirectoryW` — a bare name would be searched for starting in the exe's own folder). The tray's Open Config ignores the result: a failure there is only in the log (`open_config_err`), as before. Refresh asks Windows Location again while the config has no location.

**COM init**: `ensure_com_initialized` → `CoInitializeEx(None, COINIT_APARTMENTTHREADED)` runs first in `run()` and makes the main thread the STA that IThemeManager2 needs (§1). Since v0.6.0 the main thread makes no WinRT call: the lookup thread has the MTA (above).

### 4. Config

Exe-relative path (`current_exe().parent().join("config.json")`, never CWD). `#[serde(default)]` at struct level makes missing fields safe; `#[serde(flatten)] extra` keeps unknown keys so a save writes them back (v0.4.1).

**Broken files are never overwritten** (v0.3.2; unit-tested). `load_config_ex(path, registered) -> Result<(Config, Option<LoadNote>), String>` (`LoadNote::Healed(Healed { reason, auto_start, save_err })` or `LoadNote::NotCreated(reason)`, both below; the test-only `load_config_at` drops the note): the file is decoded by `read_config_text` (UTF-8 with/without BOM, or UTF-16 LE/BE with BOM — PowerShell 5.1's `>` default is LE; odd-length UTF-16 is an error, not a heal); missing file → first run, defaults written by `create_config` (`create_new` — never route this through rename, which replaces); content that is only whitespace/NUL/BOM → self-heals to defaults (crash leftover; `load_config_logged` logs `config_healed reason=empty action=reset-to-defaults auto_start=…`, or `action=reset-in-memory` + `config_save_err` if writing the defaults back failed); anything else unparsable → `Err`, file untouched. **A heal leaves autostart as it is** (v0.6.0): the repaired config is the pure `healed_config(registered)` — the defaults, with `auto_start` = whether the Run value exists at that moment (`registered`: `Some(true)`/`Some(false)`; `None`, the registry unreadable, keeps the default `true`). An empty file can't say what the user had chosen, and the default `true` re-registered autostart for someone who had turned it off — in that session, and through the repaired file at every later start. `registered` is a parameter of the load path (`load_config_ex`, `load_config_via`), asked only when a heal happens: production passes `auto_start_registered` (`hkcu_value_exists(RUN_KEY, APP_NAME)`, read-only, any value type counts), tests pass a constant and never read the real registry. The in-memory heal (file not writable) uses the same config. The cost (README → Known limitations): an empty file on a PC where nothing is registered yet is not a first run — it is repaired with `auto_start: false`. Two ways to get there: a crash during the very first run, before `apply_auto_start` had registered anything (it runs after `acquire_location`, whose dialogs can stay open for minutes, and `create_config` doesn't flush), and a config.json **created empty ahead of the first start**, by hand or by an installer — so the planned Scoop manifest's `pre_install` must write `{}`, which isn't empty for `config_content_is_empty` and parses to the defaults (README → Release & distribution, step 4). (A Run value deleted by an AV quarantine at the same time as the file is emptied would end the same way, and stop the re-register-at-launch recovery; two rare events at once.) A first run (no file) keeps the default `true`. **Coordinates are checked at load** (v0.6.0): `parse_config` parses the text as `Config` and then `check_coordinates` returns `Err` — the same config-error path, file untouched — for a latitude outside ±90 or a longitude outside ±180 (`config.json: latitude must be between -90 and 90`, plus one hint when it fits: `(are the two swapped?)` when the pair would be valid the other way round, or `(a 0 to 360 longitude? West is negative: subtract 360)` for a longitude above 180 up to 360 with a valid latitude — both are questions, since a digit too many gets them too), and for one of the two keys without the other (`config.json has "latitude" but no "longitude" (check the spelling). …`), whatever the value of the one that's there. **The messages name the key, never its value**: the text goes to `events.log` (`config_error`) as well as the dialog, and a slip — the two swapped, a digit too many — would put the user's real coordinates in the log. For the same reason `config_json_error` drops the value serde_json quotes in a wrong-type error: a coordinate typed in quotes gives `config.json is not valid JSON: wrong kind of value, expected f64 at line 2 column 25`, not `invalid type: string "24.713552", expected f64 …` (this applies to every key; what was expected and where are kept, and syntax and duplicate-key errors pass through unchanged). Key presence comes from a second parse into `CoordinateKeys` (`Option<IgnoredAny>` per key), because a missing key deserializes to 0.0 in `Config`; a misspelled key is just an unknown key, so it counts as missing (both misspelled is "neither": Windows Location is asked). Neither key, or both 0.0, still means "no location yet". Before this, 225 typed for 22.5 gave a schedule that was hours off, and a missing key put the schedule on the equator or the Greenwich meridian. One input that worked before is refused now: a longitude written 0 to 360 (237.67 for −122.33) happened to give the right schedule from v0.3.2 through v0.5.1 — hence the hint, and a line for the v0.6.0 release notes. As with any config error at startup, the whole file is set aside for the session, `theme_day`/`theme_night` included (below). **Defaults only go into a file that is still missing or still empty at the moment of writing** (v0.5.1; `load_config_ex` = `load_config_via(path, read_config_text, registered)`, the reader a parameter so tests can change the file mid-load). If `create_new` hits AlreadyExists, or `heal_empty_config` finds content, the file is read again. The heal re-reads and writes in place through one handle opened with share mode `FILE_SHARE_READ`, so no other program can write, replace or delete the file in between. Before v0.5.1 both cases returned the defaults as if read from disk, and acquire_location's `persist_config` then wrote them over the user's file. A heal that finds the file gone takes the first-run path. One that finds it open for writing elsewhere (still, after 4 × 100 ms of sharing-violation retries) returns `Err`: a file being written isn't an empty one, and defaults returned now would later be persisted over that save. One that can't write it (read-only) heals in memory only. Three re-reads in a row → `Err("config.json is a link to a file that can't be opened")` for a link (create_new refuses even a dangling one), else `Err("config.json kept changing …")`. Errors go through `report_config_error`: a `config_error` log line plus a MessageBox on a **detached thread** (an `AtomicBool` prevents stacking). Broken-config session policy: startup runs read-only against the file (in-memory defaults + best-effort WinRT coords, no `persist_config`, **no autostart change** — the fallback `auto_start: true` must not override a broken file's `false`). `load_config_logged` hands the config on as `Loaded { cfg, from_file }` (`Loaded::new(cfg, note)`, pure: `from_file` is false only for `LoadNote::NotCreated`). Refresh goes through the pure `adopt_reloaded_config`: a good reload is adopted; a failed one keeps the last-known-good config, and so does one that ends in `NotCreated` (next paragraph); autostart is re-asserted only if a config has come from disk at some point this session (`have_disk_cfg`) — unit-tested. `save_config_at` (replace) must only ever be called with a config successfully loaded from that file this session. Two things keep to that, neither of them a check inside `save_config_at`: `run()` never persists in a broken-config session, and `persist_config` → `persist_config_at(path, cfg, not_on_disk)` sends a `NotCreated` session to `create_config` instead (next paragraph). Accepted, and as before v0.6.0: nothing re-checks the file at the moment of the replace, so whatever was saved into it between a load and the location persist that follows (the lookup, normally under a second) is replaced — after an ordinary load, a first-run create, and a repair of an empty file alike. That includes the repair that couldn't be written (`save_err`): its config exists in memory only, the file read as empty, and the persist is what writes it (or fails like the repair did, when the file is read-only).

**A config.json that can't be created** (v0.6.0; REVIEW finding 17). On the first-run path, `create_config` failing with anything but AlreadyExists — a folder the account can't write to (Program Files), a read-only volume, a full disk — used to be dropped: the app ran on the defaults, looked up or asked for the location at every start, logged nothing (`events.log` is in the same folder) and Open Config opened a file that isn't there. `load_config_via` now returns the defaults with `LoadNote::NotCreated(<the io error's text>)`, and `load_config_logged` calls `report_config_not_created`: a best-effort `config_create_err msg="…"` line and one warning box per run of the app (`show_warning_once`) naming the folder and saying to move the exe somewhere writable. The session carries on exactly as before (`have_disk_cfg` true, the default `auto_start: true` registered — the exe is in a permanent place — and the location looked up), with one difference that keeps the defaults-only-into-a-missing-file rule: while the static `CONFIG_NOT_ON_DISK` is set (by the latest load ending in `NotCreated`; cleared by any other successful load, or once a persist creates the file), `persist_config` writes through `create_config` (`create_new`), never `save_config_at`'s rename — the session's config didn't come from a file, so it may only go into one that is still missing. Before, acquire_location's save would have replaced a file that appeared in between. In a folder that really can't be written both fail the same way (`config_save_err`). A Refresh loads again and reports again in the log; the box isn't repeated. **A Refresh that ends in `NotCreated` adopts nothing**: `adopt_reloaded_config` keeps the config the session has and returns `have_disk_cfg` unchanged, with no config error. At a Refresh "missing and can't be created" is as likely the exe's drive or share being unreachable at that moment as a deleted file (std maps `ERROR_PATH_NOT_FOUND`, `ERROR_BAD_NETPATH`, `ERROR_BAD_NET_NAME` and `ERROR_INVALID_DRIVE` to `NotFound`, and the create then fails the same way); through v0.5.1 the defaults replaced the settings loaded earlier — coordinates, theme paths — and their `auto_start: true` registered autostart over a file that said `false`. The kept config then persists create-only like any `NotCreated` session's. At startup `NotCreated` still means a first run on the defaults.

`save_config_at` is atomic (v0.4.1): write `config.json.tmp`, `sync_all`, rename over the target (retrying briefly on access-denied/sharing-violation from an AV scan); on failure the temp file is removed and `persist_config` logs `config_save_err`. Exception: if `config.json` is a symlink/junction (a name-surrogate reparse point — OneDrive/cloud placeholders don't count) or a hard link with other names (`is_linked_file` — e.g. a package manager's persisted config), it's written in place, since a rename would detach it.

`has_location()` returns false when both coords are `0.0` (null-island sentinel used for first-run detection). A `Config` only ever holds coordinates that passed `check_coordinates` (from the file), came through `usable_location` (from Windows Location), or are the 0/0 default.

**Autostart** — `apply_auto_start(cfg.auto_start)`, at startup and on Refresh (never in a broken-config session, above). It first asks the pure `auto_start_plan(enable, exe_in_temp)` → `Register` / `Remove` / `LeaveTempFolder`, and `carry_out_auto_start(plan, set_auto_start)` carries the plan out — the registry step is a parameter, so a test shows on a throwaway key that `LeaveTempFolder` never calls it — returning `Registered` / `Removed` / `LeftAlone` / `Failed { op, msg }` for `apply_auto_start` to act on (the Startup-switch note, nothing, the temp-folder report, the `autostart_err` line):

- `set_auto_start(enable)` makes the `HKCU\...\Run\WinThemeSwitcher` value match: enable reads the current value and writes the quoted exe path only if it differs (a missing value always differs — that's the AV-quarantine recovery); disable deletes it (not-found counts as success). Registry failures return `Err`; `apply_auto_start` logs them as `autostart_err`. Since v0.6.0 it is a thin wrapper over `set_run_value(key, name, command: Option<&str>)`, which takes the key path, the value name and the command line, so the tests run it against a throwaway key (REVIEW finding 9). Its `Ok(bool)` says whether a value was written or deleted — that is how the test sees "nothing is written when the value already matches": the key's last-write time can't show it, because Windows itself leaves a key alone when a value is set to the data it already has (measured on build 26300, 2026-11-11). **A missing Run key is created on enable** (finding 19) through `open_hkcu_key(path, access, create_missing)`: `RegOpenKeyExW` first, and only when that says `ERROR_FILE_NOT_FOUND` and `create_missing` is set, `RegCreateKeyExW` — so with the key in place (every profile has it) the app makes exactly the registry calls it made before. Disable never creates: a missing key means there's nothing to remove. Error text keeps its shape, naming the API that failed: `RegOpenKeyExW Run rc=5`, `RegCreateKeyExW Run rc=…`, `RegSetValueExW Run rc=…`, `RegDeleteValueW Run rc=…`. `RegKey` closes the handle on drop.
- **Temporary folder** (`LeaveTempFolder`): with `auto_start` on and the exe running from a temporary folder — started from inside the zip, which Explorer extracts to `%TEMP%\Temp1_<zip>\`, or from an archiver's or browser's temp folder — the Run value is left exactly as it is (one that exists may belong to the real install), `autostart_skipped reason=temp-folder` is logged once per run, and one warning box per run says to extract the zip to a permanent folder. `auto_start: false` still removes the value from anywhere. `exe_in_temp_folder()` (computed once) = the pure `in_temp_folder(exe spellings, temp-folder spellings)`: each side is the path as given plus its `fs::canonicalize`d form (`path_spellings` — long names, links followed), because %TEMP% is often stored in 8.3 form (`C:\Users\LONGUS~1\AppData\Local\Temp`; on GitHub's runners too) while `current_exe()` is long, or the reverse, and no string comparison sees through a short name. `path_key` folds the rest: a `\\?\`/`\\.\` prefix (`\\?\UNC\` = `\\`), `/`, letter case, repeated and trailing separators; the comparison is name by name, and the exe must be below the folder. The temp folders are `%TMP%`, `%TEMP%`, `%LOCALAPPDATA%\Temp` and `%SystemRoot%\Temp` (`temp_folder_spellings`, over the pure `temp_folders(var)`, which takes the environment lookup as a parameter; an unset or empty variable adds nothing) — **not `GetTempPathW` / `std::env::temp_dir`**, which fall back to the profile folder when TMP and TEMP are unset, and would then make the recommended install folder temporary. A temp folder that is only a drive or share root, or not absolute, is ignored (TEMP=`D:\` must not make every exe on D: temporary). Not recognised: an archiver set up to extract somewhere else, and the Downloads folder. The exe's path goes into the box, never into `events.log`.
- **Windows' Startup switch** (finding 20): after a successful `Register`, `note_startup_switch` reads `HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\StartupApproved\Run\WinThemeSwitcher` (`read_hkcu_value`, read-only) and, when the pure `startup_switch(type, data)` says `Off`, logs `autostart_disabled_in_startup_settings` once per run (`startup_switch_note_due(key, name, logged)` is the reading, the verdict and the once-latch together, with the key a parameter for the tests) — the explanation for "auto_start is true but the app doesn't start". **The value is never written**: the switch in Settings → Apps → Startup / Task Manager → Startup apps is the user's, and overriding it is malware behaviour and an AV signal. The format is undocumented: 12 bytes of REG_BINARY, a little-endian DWORD of flags and then a FILETIME (when it was switched off; zero while on). On this PC (build 26300, read 2026-11-11) every HKCU entry, this app's included, is `02 00 00 00` + eight zero bytes, and HKLM's SecurityHealth is `06 …`; all were on. "Off = lowest flag bit set" (03, 07) comes from how startup managers read the value, **not from a disabled sample on this PC** (none existed, and writing one for an experiment is ruled out) — if an entry you switched off produces no line, read the value and compare. Anything that isn't exactly 12 bytes of REG_BINARY is `Unknown` and nothing is said. An entry may also have no record at all, which means on like a `02` one, and nothing is said either: on this PC all 7 HKCU Run entries have a `02` record with a zero time, while 3 of the 5 HKLM Run entries have none (what makes Windows write a record wasn't observed).

### 5. Wake on session unlock / power resume

The wake ticks exist to reconcile the moment the user is back (a transition may have passed while locked or asleep) and to apply the override-preservation rule; the clock-step handling in §2 covers wall-clock jumps. (The original v0.2.0 rationale — "`Instant` pauses across suspend, so a deadline would fire ~22 h late" — is likely wrong on Windows, where `Instant` is QPC-based and winit fires ResumeTimeReached on the first wake past the deadline; the observed misses predated tier 1, when the ShellExecute path silently failed in exactly those contexts.)

`start_wake_listener` registers the power callback, then spawns a worker thread that creates a hidden message-only window (`HWND_MESSAGE`) for the session notification:

- `WTSRegisterSessionNotification(hwnd, NOTIFY_FOR_THIS_SESSION)` → `WM_WTSSESSION_CHANGE`; we act on `WTS_SESSION_UNLOCK`. Up to 3 attempts 2 s apart (terminal services may not be up at logon autostart).
- `register_power_resume()` (v0.4.1, called before the window thread starts): `PowerRegisterSuspendResumeNotification(DEVICE_NOTIFY_CALLBACK, &DEVICE_NOTIFY_SUBSCRIBE_PARAMETERS{power_callback}, ..)` — the parameters are leaked (must outlive the registration). `power_callback` runs on a system thread and sends `Wake(Power)` on `PBT_APMRESUMEAUTOMATIC` (sent on every resume; `PBT_APMRESUMESUSPEND` would only duplicate it). **Before v0.4.1 this passed `DEVICE_NOTIFY_WINDOW_HANDLE` + the hwnd — the function accepts ONLY `DEVICE_NOTIFY_CALLBACK`, so it failed with 87 (`ERROR_INVALID_PARAMETER`) on every launch and the resume hook never fired; unlock events masked it.** The callback form is also independent of whether a message-only window would receive `WM_POWERBROADCAST` (undocumented). A remaining `stage=power_register` error is real; its code is the function's return value (not `GetLastError`). This wake can arrive while the session is still at the lock screen; the later unlock is then a no-op (`SkipInSync`, or `SkipOverride` when sync is undecidable or an override is being preserved). **Still unverified on real hardware** — sleep, resume, and confirm a `cause=wake-power` line (the sign-in-on-wake setting doesn't matter: `PBT_APMRESUMEAUTOMATIC` is sent on every resume).

Both routes call `proxy.send_event(AppEvent::Wake(WakeKind::Unlock | WakeKind::Power))` via a process-wide `OnceLock<EventLoopProxy<AppEvent>>` (the WindowProc is `extern "system"` and can't capture). The main loop ticks with `TickKind::Wake` (`cause=wake-unlock` / `cause=wake-power`). Idempotent across both events firing in sequence.

`WTS_SESSION_UNLOCK` (0x8) is a local `WPARAM` const for direct comparison in the WindowProc; `PBT_APMRESUMEAUTOMATIC` and `DEVICE_NOTIFY_CALLBACK` are imported from `windows_sys::Win32::UI::WindowsAndMessaging` (not RemoteDesktop/Power, where you'd look first).

**Why this doesn't resurrect the manual-override-fight bug**: neither event fires when the user changes theme in Settings.

**Manual-override preservation (v0.4.0)**: a manual override (Settings or Toggle Theme) *survives* lock/unlock and wake-from-sleep. The rule is time-based: `TickState.reconciled_next` records the next-transition instant from the last tick that ended in sync; a Wake tick — or a Scheduled tick that runs before `reconciled_next`, which since `plan_wake` never ticks early can only be a clock-jump tick — skips the re-apply only when no transition has passed (`now < reconciled_next`, log `applied=skip-override`) and no retry is pending. v0.4.1 adds a **frame rule**: if a backward clock step was *observed* (`clock_step_ms` against the pre-tick mark < −60 s) and the schedule's upcoming transition is now more than 60 s *earlier* than `reconciled_next`, the clock was stepped back across a transition — the divergence is the app's own stale apply, so it re-applies. (Gated on an observed step because `next` can also move earlier legitimately, e.g. a polar-season crossing coming within the 48 h search.) A FAILED apply never advances `reconciled_next` (a retry leaves it stale, an exhausted budget clears it) so later wakes re-apply (a free retry). Overrides reset at the next natural transition and do not survive a process restart.

### 6. Tray + menu

Menu: Toggle Theme, Open Config, Refresh, separator, Quit. Menu events flow through `MenuEvent::set_event_handler` → `EventLoopProxy::send_event(AppEvent::Menu(id))` so clicks wake the loop. `TrayIconEvent::set_event_handler` is set to a no-op (v0.4.1): without a handler tray-icon queues every mouse event over the icon in an unbounded channel nothing drains.

**tray-icon 0.25 (v0.5.0, was 0.19)**: `build()` no longer fails when the taskbar isn't up (at an early login it keeps its window and adds the icon on `TaskbarCreated`) — but it also silently ignores a failed `NIM_ADD` from a taskbar that *is* up. So `tray_registered` probes after `build()` with `set_tooltip` (`NIM_MODIFY` fails for an unregistered icon): on failure it logs `tray_register_pending`, and `AppEvent::TrayProbe(n)` re-checks every 20 s (a worker thread sleeps, the main thread probes — `TrayIcon` is not `Send`); a still-missing icon gets tray-icon's own remove + add by `SendMessageW(tray.window_handle(), RegisterWindowMessageW("TaskbarCreated"))`; after 6 attempts, `tray_register_failed` + a non-blocking warning box. Log lines: `tray_registered attempt=N`, `tray_register_retry attempt=N ok=…`. The menu now opens on button **release**.

**Toggle Theme** resolves both slots, reads `read_modes()`, and applies `toggle_target(screen, day.modes, night.modes, decidable, last_applied_slot(), fallback)` via `apply_theme` directly (pure, unit-tested): when decidable, a screen matching the day slot → night, matching night → day, matching neither → whichever the apps mode isn't; when undecidable or unreadable → the opposite of the slot this process last applied successfully (`LAST_APPLIED_SLOT`, a process-local static set by `note_applied_slot` after every successful tick or toggle apply — deliberately **not** in `TickState`), else of the schedule's current slot (day without location). It does **not** call `tick()`, does not disturb the pending wait, and changes nothing `TickState` knows about the schedule (`reconciled_next`, `armed`, `mark`). That's what makes it a manual override. The one thing it writes there is `note_toggle`'s flag on a pending retry, and only when its apply returned Ok (§2); the retry tick itself still runs, logs `applied=skip-user-intervened` and arms the next transition. Known accepted race: a toggle within ~5 s of a *tier-2* apply can be reverted by that apply's still-running commit_watcher (only when that apply went through tier 2 — a failing tier 1, or a theme it refuses by design).

Tray icon is generated in `make_tray_icon`: 32×32 RGBA, half orange (sun) + half dark-blue (moon). Procedural because `tray-icon`'s default placeholder is near-invisible on both taskbar modes; `with_icon` is required for the icon to show.

### 7. Fail-loudly plumbing (v0.4.0)

`main()` is a thin wrapper: `install_panic_hook()` (writes `panic at=file:line:col msg="…"` via `log_event_from_panic`, which only `try_lock`s `LOG_LOCK` — a panic while holding it must not deadlock instead of aborting) → `claim_single_instance()` (`CreateMutexW("Local\\WinThemeSwitcher.single-instance")`, read by the pure `instance_claim(handle is null, last error)`: a handle with `ERROR_ALREADY_EXISTS` → another copy → log `duplicate_instance action=exit`, info MessageBox, exit 0; no handle with `ERROR_ACCESS_DENIED` → the mutex exists but this process may not open it (v0.6.0) → the same notice and exit, logged as `duplicate_instance action=exit reason=access-denied`, once `OpenMutexW(SYNCHRONIZE)` (`probe_mutex`) has confirmed the name is there (`mutex_name_taken`: it opened, or failed with anything but `ERROR_FILE_NOT_FOUND`). If the name isn't there, either the other copy exited between the two calls or creating a named mutex is what this process is refused, so the pure `settle_instance_claim(create, probe)` — the two calls as closures, which is how its sequences are unit-tested — runs one more round: a mutex created then makes this the first copy, holding the lock; refused twice with nothing there is a creation failure. Any creation failure logs `single_instance_err code=N` and continues; the handle is intentionally leaked. Which claims end the process, and the exact log text, is the pure `InstanceClaim::duplicate_log`, the only thing `main()` reads. The log line is best effort: `write_log_line` drops a line it can't write, and a low-integrity copy — the one case reproduced that gets access denied — can't append to `events.log` in an ordinary folder (tried 2026-11-11 with a low-integrity token on a file under `%LOCALAPPDATA%`: error 5), so there the notice box is the only sign and the log shows nothing) → one log line, `app_start version=X.Y.Z` (v0.6.0; the const `APP_START`, from `env!("CARGO_PKG_VERSION")` — the version the exe's version resource and manifest carry too; written only by a copy that got past the single-instance check, so a second copy that exits never writes it, and before `run()`, so before the config is read and the first tick; nothing else is in the line — no path, user name or coordinates) → `run()`. Any `Err` from `run()` — tray-window creation, event-loop build/death — logs `fatal_error msg="…"` and shows a blocking MessageBox before exit 1. (A taskbar not ready at login no longer fails `build()`; see §6 for how a missing icon is detected.) The warning boxes that must not block (config errors, rejected theme paths, a missing tray icon, and since v0.6.0 a config.json that couldn't be opened for the user at first run, §3) go through `show_warning_async(flag, title, body)`: a detached thread, one `AtomicBool` per kind so repeats don't stack. Two more (v0.6.0) are about things that can't change while the app runs — the exe in a temporary folder (`report_temp_folder`), and a folder where config.json can't be created (`report_config_not_created`), both §4 — and go through `show_warning_once(shown, title, body)`: the same detached thread, but its flag is never reset, so each shows once per run of the app however often Refresh is chosen. All quoted `msg="…"`/`path="…"`/`display="…"` fields flow through `sanitize_log_msg` (quotes→apostrophes, newlines→spaces).

**When the single-instance mutex can't be opened** (checked 2026-11-11, Windows 11 build 26300, from a non-elevated shell with throwaway mutex names). `CreateMutexW` asks for `MUTEX_ALL_ACCESS` on an existing mutex and fails with `ERROR_ACCESS_DENIED` (no handle) when that isn't granted. Who gets that: a copy started with **fewer rights than the first** — reproduced for a low-integrity token against a mutex made at normal integrity (the mutex is implicitly medium integrity, and full access includes write access): error 5, while `OpenMutexW(SYNCHRONIZE)` opened it and creating a new name at low integrity worked. **An elevated first copy, which the roadmap item named, does not cause it**: a mutex created without a security descriptor in `Local\` takes its access list from the session's `\Sessions\<n>\BaseNamedObjects` directory, whose inheritable entries give full access to SYSTEM, the creator/owner and the session's logon SID — not from the creator's token (the elevated token's default DACL, Administrators + SYSTEM full and the logon SID read/execute, would refuse a non-elevated copy; a throwaway mutex given that list did return error 5). The non-elevated copy has the same logon SID, and mutexes made by elevated or SYSTEM processes carry no high-integrity label (of 10 such mutexes in the session, 8 had the inherited list and all 8 opened with full access; the other 2 carried an explicit low label), so the ordinary `ERROR_ALREADY_EXISTS` path already stops a second copy there. Read from the directory's security descriptor and those mutexes; **not run with an actual elevated copy of the app**. An elevated second copy after a normal first one opens the mutex like any other. Unchanged: the mutex is per session (`Local\`), so a copy in another session of the same account isn't seen; a name taken by another kind of object (`ERROR_INVALID_HANDLE`) or any other creation failure still lets the app run.

### Reading events.log

Main line: `<rfc3339> cause=<c> current=<m> target=<m>[ slot=day|night][ sync=undecidable] applied=<a> next=<rfc3339>`, or on a failed apply `… err="…" retry=N|exhausted next=<rfc3339>`, plus `cause=toggle current=… target=…[ slot=…] applied=…` for Toggle and `cause=<c> skipped=no-location` without coordinates.

- `current=`/`target=`/`actual=` values (`modes_str`, no `=` or `,` inside): `light`, `dark`, `apps-light/system-dark`, `apps-dark/system-light`, `unknown`. With stock themes `target=` reads as before v0.5.0; `current=` now shows a mixed value when the screen's apps and taskbar modes differ (v0.4 printed only the taskbar's), and `unknown` if either value is unreadable. `slot=` appears only when the target modes don't name the slot (a mixed or opposite-mode theme) or sync is undecidable.
- `cause=`: `init`, `resume-time` (deadline due), `clock-jump` (clock step detected — preceded by `clock_jump step_s=±N consumed_by=clock-jump`), `refresh`, `wake-unlock`, `wake-power`, `toggle`.
- `applied=`: `theme-manager2` (tier 1, healthy), `theme-file` (tier 2), `registry` (tier 3), `skip` (already on target), `skip-override` (manual override preserved — or, with `sync=undecidable`, simply no transition since the last apply), `skip-user-intervened` (retry stood down: the screen moved off the reading the failure left, or — since v0.6.0's Toggle flag, with `current=` possibly unchanged or `unknown` — a `cause=toggle … applied=…` line was logged since the failure).
- `app_start version=X.Y.Z` (v0.6.0): the first line of each run — which version wrote the lines that follow, up to the next `app_start`. Only a `single_instance_err` line can precede it in its run (the single-instance check comes first, so that a second copy never writes `app_start`): such a line right above an `app_start` belongs to that start. A second copy that exits at the single-instance check writes `duplicate_instance` instead. Logs from v0.5.1 and earlier have no such line.
- Companion lines: `theme_manager2_apply` (tier-1 success: display name, index, `after_ms`, and since v0.5.1 `readback=reached|already-matching|modes-not-in-theme-file|unreadable readback_ms=N`), `theme_manager2_noop target=… actual=… display=… idx=… after_ms=… readback_ms=…` (SetCurrentTheme reported success but the modes never reached the target; tier 2 follows), `theme_manager2_err`, `theme_manager2_enum_skip`, `theme_manager2_ambiguous display="…" matches=[…] using_idx=N`, `theme_path_rejected` (replaced v0.4's `theme_path_missing`; since v0.6.0 also `reason=network-path` — the configured file is on a share or a network drive and was refused unopened, so the line says nothing about whether it exists), `theme_sync decidable=… reason=… day=… night=…` (only when that changes; silent while decidable), `modes_read_err value=… err=…` (once), `settings_closed`, `commit_observed`, `commit_unverifiable`, `commit_timeout` → `fallback_registry` / `fallback_registry_err`, `config_error`, `config_healed reason=empty action=reset-to-defaults|reset-in-memory auto_start=true|false` (an empty or NUL-filled config.json was reset; since v0.6.0 `auto_start=` shows what the repaired config got — whether autostart was registered at that moment, §4), `config_save_err`, `config_create_err msg="…"` (v0.6.0: config.json is missing and couldn't be created — at a first run usually a folder that can't be written, in which case this line can't be written either and the warning box is the only sign; seeing it means the log was writable and something else failed, e.g. a full disk. At a Refresh — the file deleted, or its drive not reachable — the session keeps the config it had, §4), `location_rejected reason=out-of-range|zero` (Windows Location returned something that isn't a place on Earth, or exactly 0/0; the values are not logged), `location_lookup_failed reason=access-denied|access-unspecified|timeout|error|reading-rejected after_ms=N` (v0.6.0: one line for every Windows Location lookup that gave no location — at a first run, at the start of a broken-config session, at a Refresh without coordinates — never with coordinates. `access-denied`: Windows said the app may not use the location — Location is off, or not allowed for apps; `access-unspecified`: it said neither yes nor no; `timeout`: no answer within the 15 s cap, `after_ms` ≈ 15000 — the lookup may still finish, and its answer is dropped; `error` adds ` stage=apartment|request-access|geolocator|position|reading|worker hresult=0x…`, the call that failed and its HRESULT (`worker` with zeros: the lookup thread couldn't start or ended without an answer); `reading-rejected` adds ` reading=zero|out-of-range` and follows the `location_rejected` line. - Healthy: `applied=theme-manager2` (its `theme_manager2_apply` line shows `after_ms` ~150–700 and `readback=reached`, or a reason the modes can't show it), or `applied=skip`. ## Invariants — don't break these

- **`tick()` scope**: only Init / ResumeTimeReached-when-`plan_wake`-says-Tick / Refresh / `AppEvent::Wake`. Adding a callsite for any *other* trigger — especially anything that fires on `WM_SETTINGCHANGE` — resurrects the manual-override-fight bug. `WaitCancelled` must never tick (it may only set the control flow).
- **Only `tick()` writes `TickState.armed`/`mark`** (via `arm()`, or clearing them without location). The clock-step check measures from the mark; re-marking anywhere else (e.g. on a heartbeat or a WaitCancelled) would hide a step.
- **STA thread for IThemeManager2**: `ensure_com_initialized` runs `CoInitializeEx(None, COINIT_APARTMENTTHREADED)` first in `run()`. All theme apply runs on that thread. The Location lookup's thread and its MTA (v0.6.0) are separate and change nothing about this.
- **`poke_shell` after tier-2 / tier-3 apply only** — tier 1 broadcasts internally; adding it back re-introduces the AV-tripping `HWND_BROADCAST WM_SETTINGCHANGE` signal.
- **Refresh forces apply** (bypasses state check); scheduled transitions respect it. Don't invert.
- **`decide_tick` reads the PRE-tick state**; `settle_tick` (→ `note_reconciled`/`note_apply_failed`) runs after the apply outcome is known, and it is the only place a tick records an outcome. A failed apply must never advance `reconciled_next` (retry: leave it stale; exhaustion: clear it). Never "simplify" by assigning state before/regardless of the outcome.
- **The retry baseline is read AFTER the failed apply** (`TickOutcome::ApplyFailed { after: read_modes() }`, built in the Err arm), never the pre-tick reading — otherwise a partial apply looks like the user's move and the retry cancels itself.
- **Tier 1's read-back stays registry-only, and a `NoOp` falls through exactly like an Err.** Only a successful reading that isn't the target makes a no-op — an unreadable registry never does — and nothing is read back when `unverifiable_reason` says the modes can't show it (there, a no-op looks like success).
- **Defaults go only into a config.json that is missing (`create_new`) or still empty (re-checked through the heal's `FILE_SHARE_READ` handle)**; any other outcome reads the file again. Never return defaults as if they came from a file that wasn't read. A session whose config.json couldn't be created (`LoadNote::NotCreated`, `Loaded::from_file` false, `CONFIG_NOT_ON_DISK`) persists through `create_new` only, never the replacing `save_config_at` — and a Refresh that ends that way adopts nothing: the session keeps the config it has (`adopt_reloaded_config`), never the defaults. (A repair of an empty file counts as read from the file, written or not; its later persist replaces the file like any other load's, §4.)
- **A repaired (empty) config.json takes `auto_start` from what is registered, never from the default** (`healed_config`); the first run keeps the default `true`. The "is it registered" reading is a parameter of `load_config_ex`/`load_config_via`, asked only for a heal: tests pass a constant.
- **The app never writes under `Explorer\StartupApproved`** — it reads the user's Startup switch to explain it in the log (`note_startup_switch`), and the switch always wins. Nor does it point the Run value at an exe in a temporary folder (`auto_start_plan`); there the existing value is left untouched, not removed.
- **Registry tests work only under their own throwaway key** (`TestKey`, `HKCU\Software\WinThemeSwitcherTest-…`, removed on drop): never the real Run, StartupApproved or Personalize keys. That is why `set_run_value`, `write_modes_at`, `read_hkcu_dword`, `read_hkcu_value` and `hkcu_value_exists` take the key path — keep new registry code parameterised the same way, with the real key only in a thin wrapper.
- **`autostart_skipped` and `config_create_err` carry a reason, never the exe's path** (in a temporary folder it names the user's profile and the download); the path is shown in the warning box only.
- **Coordinates are checked where they enter**: config.json in `parse_config`, Windows Location in `usable_location` — which the lookup thread's reading reaches through `settle_location`, on the caller's thread, and by no other way. `schedule` computes something for any numbers, so nothing else may put coordinates into a `Config`. Only Windows Location readings are rounded; never rewrite coordinates the file already has. Coordinates never go into `events.log`: a coordinate error names the key, not the value, `config_json_error` strips the value serde_json would quote for a wrong type, and `location_lookup_failed` carries a reason, a time and for an error a stage and an HRESULT, never a reading. A test that looks up the real location prints the outcome only, and its assertions carry no values.
- **Resolve slots once, compare and apply the same `Slot`**: the modes a tick/toggle decides against must come from the file `apply_theme` applies (post path-policy, post stock fallback). Never read modes from the configured path, and never cache slots across ticks (files change; Refresh reloads).
- **Nothing opens a configured theme path before `on_network` has passed it**: the check is text (put in the form Win32 opens by `std::path::absolute`, which is string work) plus `GetDriveTypeW`, and sits in `check_theme_path` ahead of the first `is_dir`. What `on_network` can't recognise is listed under Theme path policy (links, some `subst` drives, device names other than a drive letter); passing it is not proof the path is local. A call that looks at the file (`exists`, `metadata`, `canonicalize`, an open) placed before it — or made on the configured path anywhere outside `check_theme_path` — brings back the 20–40 s freeze for a share whose server is down.
- **Toggle Theme never ticks, and in `TickState` it only calls `note_toggle`** — it's a manual override by construction. `note_toggle` sets `retry_toggled` on a pending retry and nothing else: Toggle must never change `reconciled_next`, the retry count, baseline or window, `armed` or `mark`, and `retry_toggled` is set only when the Toggle's apply returned Ok. Its memory of the last applied slot lives in the process-local `LAST_APPLIED_SLOT`, not `TickState`.
- **Only `scripts\release.ps1` writes GitHub releases.** No workflow may run on a tag or write (the script's allowlist refuses a tree whose workflows aren't exactly a branch-filtered, read-only `ci.yml` — exit 29), and never re-run an old Release workflow run (CI and releases section).
- **Publishing is irreversible** (immutable releases): never publish anything but a verified draft, never delete-and-republish a release (the tag name is burned), and before editing any still-mutable old release, verify its assets — the edit freezes them.
- **`THIRD-PARTY-NOTICES.txt` is generated, never hand-edited, and ships in every release zip.** It must match `Cargo.lock` (CI step; `release.ps1` exit 31 before anything is built or published). `scripts\notices.ps1` must stay deterministic: nothing in its output may depend on the machine, the date, the culture or the toolchain — which is why the Rust standard library's entry is fixed text that has to be re-checked by hand after a Rust update. The release notes must name the file (`release.ps1` exit 26 otherwise): the exe is also published on its own.
- **Capture `GetLastError()` into a local immediately** after the failing Win32 call — `Local::now()`, `log_event`, and `format!` all make Win32 calls that clobber it.
- **`SetDefaultDllDirectories` stays the first call in `main()`**, and everything the app loads must be a System32 DLL (or COM/WinRT-activated by full path). One exception, by the manifest: `comctl32.dll` version 6 comes from `%SystemRoot%\WinSxS` (Build → Manifest and version resource). Don't add a manifest dependency on any other side-by-side assembly without the same evidence.
- **`app.manifest` never gains `longPathAware`, `activeCodePage` or any other setting that changes how Windows APIs behave** — the app handles long paths itself in `\\?\` form, and with `longPathAware` the test of that would pass without showing anything. `build.rs` and `check-hardening.ps1` both refuse it. Keep `asInvoker`: the app must never ask for elevation. **And the Common-Controls dependency never gets a `language` attribute.** The snippet everyone copies has `language="*"`; with it Windows looks for the assembly in a folder named for the UI language next to the exe before it looks in WinSxS, and `en-US\Microsoft.Windows.Common-Controls.manifest` plus `en-US\comctl32.dll` planted there were loaded by the signed release exe (seen 2026-11-11 by starting a copy from a scratch folder; `/DEPENDENTLOADFLAG:0x800` and `SetDefaultDllDirectories` don't apply, since side-by-side redirection comes before any search). Without the attribute the same plant is ignored and comctl32 6 comes from WinSxS (same test). `check-hardening.ps1` (exit 7) and the manifest test refuse the attribute. Not covered by any of this: whoever can write to the app's folder can still replace the exe itself.
- **The version is written in one place, `Cargo.toml`.** The manifest, the version resource and the `app_start` log line all take it from cargo at build time; never type a version into `app.manifest`, `build.rs` or `main.rs`. `check-hardening.ps1` compares the built exe with `Cargo.toml` and stops `build.ps1` (exit 7) and CI on a difference.
- **No crates and no SDK tools in `build.rs`**: it writes the `.res` by hand, so `Cargo.lock`, `deny.toml` and the notices don't know about it and the build needs only what linking needs. After changing the bytes it writes, compare with `rc.exe`'s output once (Build section) and run both resource tests.
- **Run cargo from the repo directory, never with `RUSTFLAGS` set** (or `.cargo\config.toml` silently doesn't apply). Run tests via `scripts\test.ps1`, release builds via `scripts\build.ps1`.
- **Never relaunch the deployed app as a child of an agent shell** (MSIX container → virtualized HKCU); use `explorer.exe "<exe>"` as `build.ps1` does. Never deploy into AppData from a packaged shell either (new files and folders there can land in the package's private store; `build.ps1` refuses with exit 9).
- **Free BSTRs from `ITheme::GetDisplayName` with `SysFreeString`** — not `CoTaskMemFree`, and never leak.
- **Vtable order in `IThemeManager2Vtbl`**: every method's slot index must match the COM ABI. The struct declares every slot up through `set_current_theme` — uncalled interior slots are `_`-prefixed placeholders that are **mandatory padding, never removable**; only trailing slots after the last called method may be omitted, and nothing may ever be reordered.
- **The Windows Location lookup runs only on its own thread** (`lookup_windows_location` → `run_with_timeout` → `query_windows_location`), never on the main thread, and its caller waits at most `LOCATION_LOOKUP_CAP`. The worker can be abandoned at any moment, so it owns everything it touches and reports only through its return value: nothing in it may touch the config, the registry, the log or the UI. It makes no `CoInitializeEx` call of its own — it is in the MTA that `keep_mta_alive` creates and never releases (§3) — and the main thread, which makes no WinRT call any more, stays an STA.
- **A location dialog says only what the app knows.** Its text comes from the pure functions (`location_prompt`, `location_settings_followup`, `manual_setup_text`, `no_config_file_text`, `config_not_opened_text`), whose inputs are the failure, whether Settings could be opened, whether the tray icon exists and whether there is a config.json to type into; a new sentence goes into them and into their test tables. The callers that feed them (`explain_missing_location`, `open_location_settings`) have no tests — keep them thin. "Off or not allowed" belongs to `LocationFailure::Denied` alone, that Settings opened is said only after `ShellExecuteW` returned > 32, and a box shown before the tray exists says that the icon appears once the box is closed before it says to click it.
- **UTF-16 + NUL**: all Win32 wide strings go through `wide()`, which appends the terminator. Never pass a bare `&str` to a `*W` API.
- **HWND null check**: `(hwnd as usize) == 0` — robust to `windows-sys` flipping between `*mut c_void` and `isize`.
- **Windowed subsystem** (`#![windows_subsystem = "windows"]`): no console, `println!` goes nowhere — and it applies to the test binary too (see `test.ps1`). For diagnostics, write to `events.log`.
